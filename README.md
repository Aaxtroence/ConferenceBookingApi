# Conference Room Booking API

REST API сервіс для управління конференц-залами, бронюваннями та розрахунком вартості оренди з урахуванням динамічних тарифів.

## Технології

- ASP.NET Core Web API (.NET 10)
- Entity Framework Core + SQLite
- Swagger / Swashbuckle
- xUnit + EF Core InMemory (unit-тести)

## Запуск проєкту

```bash
cd ConferenceBookingApi
dotnet restore
dotnet ef database update
dotnet run
```

Swagger UI: `https://localhost:xxxx/swagger` (порт вказано в консолі після запуску)

При першому запуску база даних автоматично наповнюється початковими залами й обладнанням (`Data/SeedData.cs`).

## Запуск тестів

```bash
dotnet test
```

## Архітектура та особливості

Тонкі контролери: Вся бізнес-логіка, валідація та перевірки винесені в сервіси (IRoomService, IBookingService, IPricingService), що полегшує тестування.

Централізована обробка помилок: ExceptionMiddleware перехоплює кастомні винятки (ValidationException, NotFoundException, ConflictException) та перетворює їх на відповідні HTTP-статуси (400, 404, 409).

Безпека видалення: Зал із активними майбутніми бронюваннями (EndTime > UtcNow) видалити не можна — система поверне конфлікт (409), захищаючи розклад від ламання.

## Логіка розрахунку ціни

Вартість розраховується погодинно через PricingService, який винесено в чисту функцію без прив'язки до бази даних:

| Діапазон | Множник |
|---|---|
| 06:00–09:00 | ×0.90 (знижка 10%) |
| 09:00–12:00 | ×1.00 (базова вартість) |
| 12:00–14:00 | ×1.15 (пікові години, націнка 15%) |
| 14:00–18:00 | ×1.00 (базова вартість) |
| 18:00–23:00 | ×0.80 (знижка 20%) |
| поза 06:00–23:00 | бронювання заборонено (400) |

**Краєві випадки:**
- **Бронь не кратна годині** (наприклад 10:00–10:30) — вартість рахується пропорційно частці години (`PricingService.CalculateRoomCost` розбиває інтервал на "шматки" по межах годин, а не тільки по цілих годинах).
- **Ціна фіксується в момент бронювання** (`Booking.TotalPrice`) і не перераховується, якщо адміністратор пізніше змінить `BasePricePerHour` залу - інакше клієнт побачив би іншу суму, ніж ту, на яку погоджувався.
- **Бронювання поза робочими годинами** (до 06:00 або після 23:00) — відхиляється з кодом 400.

## Ендпоінти

POST /api/rooms — створення залу
PUT /api/rooms/{id} — редагування залу
DELETE /api/rooms/{id} — видалення залу
GET /api/rooms/available - пошук вільних залів за параметрами

POST /api/bookings — створення бронювання

GET /api/reports/revenue — звіт по доходу за період
GET /api/reports/occupancy — звіт по відсотку зайнятості залу

## Тестування

Проєкт покритий модульними тестами (xUnit + EF Core InMemory), які перевіряють розрахунки цін, логіку сервісів та краєві випадки:

PricingServiceTests — тарифи, пікові години, дробові інтервали, валідація часу.
RoomServiceTests — CRUD залів, перевірка зв'язків та активних броней.
BookingServiceTests — конфлікти розкладу та правильність підсумкової вартості.

`PricingService` навмисно спроєктований як "чиста функція" без залежності від бази даних — це найлегший кандидат для unit-тестування, і його коректність перевірена окремо від решти системи.

## Що б я покращив у продакшені

- Авторизація/автентифікація відсутня — завдання цього не вимагало, але для реального продукту потрібна.
- Race condition при одночасному бронюванні - я додав би унікальний constraint у базу даних, щоб уникнути подвійного бронювання на той самий час.

## Як би я масштабував цей проєкт

- Перехід на "серйознішу" базу даних — SQLite чудово підходить для тестового завдання і невеликих проєктів, але не розрахований на багато одночасних записів. У продакшені я б використав PostgreSQL або SQL Server.
